# Афиша культуры Башкортостана

Единая достоверная афиша культурных событий республики: **веб-сервис + Telegram-бот + открытый REST API + ИИ-агент**.
События из разных источников склеиваются без дублей, у каждого есть статус (состоится, перенесено, отменено, билеты проданы),
а запрос обычным языком («куда пойти в субботу с ребёнком до 1000 рублей») превращается в подборку с объяснением.

> **База знаний проекта:** [docs/README.md](docs/README.md): архитектура, запуск, выкладка на сервер и эксплуатация, безопасность, решения и грабли.

> **Неофициальный сервис.** Проект не является сервисом Министерства культуры Республики Башкортостан и не связан с ним.
> Данные собраны из открытых источников (culture.ru, Яндекс Афиша, Kassir.ru), перед визитом их нужно уточнять у организатора.
> Эта пометка показывается на сайте, в боте, в виджете и в описании API.

## Выбранный уровень решения

**Уровень 2 «Сайт»** по ТЗ (§5): Telegram-бот, веб-каталог, REST API и виджет. Уровни кумулятивные, поэтому сюда входят и
требования уровня 1. Поверх этого уже работает ИИ-агент из уровня 3, но уровень 3 не заявляется: у агента нет трассировки,
подсчёта стоимости и набора контрольных запросов.

Что для уровня 2 ещё не закрыто (подробно, с номерами пунктов ТЗ: [upd.md](upd.md)): админ-интерфейс, форма обратной связи,
страница события с постоянной ссылкой, версия API в адресе, единый формат ошибок, кеширование, метрики, журнал изменений,
хранение сырых данных источников.

## Что из требований кейса где реализовано

| Требование кейса | Где |
|---|---|
| Telegram-бот | `app/bot.py`: меню быстрых фильтров, выбор города, категории, свободный текст через агента |
| Веб-сервис с поиском и фильтрами (дата, город, цена, возраст, категория) | `app/static/` + `GET /api/events` |
| Статусы событий | поле `status`, PATCH-метод, отменённые скрыты по умолчанию и перечёркнуты в интерфейсе |
| Дедупликация, выдуманных мероприятий нет | `app/dedup.py`, `app/ingest.py`; число подтвердивших источников видно в карточке |
| ИИ-агент: свободный запрос, уточнения, объяснение подборки | `app/agent.py` (Gemini + инструменты поиска по нашей БД) |
| Открытый REST API, документация | `/docs` (Swagger), `/openapi.json`, CORS открыт на чтение |
| Виджет для сайта министерства без вмешательства в его системы | `/widget.js`, пример на `/widget-demo` |

## Запуск одной командой (Docker)

```bash
docker compose up --build            # сайт и API: http://localhost:8000, документация: /docs
docker compose --profile bot up --build   # то же и Telegram-бот (нужен TELEGRAM_BOT_TOKEN в .env)
```

Нужен только Docker. Файл `.env` необязателен: без него работают сайт, API и режим «без ИИ» (образец: `.env.example`).
При первом запуске подгружается `data/sample_events.json`: 120 реальных событий из открытых афиш на 13.11.2026 (источник
записан у каждого, повторная загрузка дублей не создаёт). Отключить: `LOAD_SAMPLE_DATA=0`. База хранится в томе
`afisha-data`, порт меняется переменной `WEB_PORT`. Образ строится из PyPI; на сервере без доступа к PyPI используется
`deploy/Dockerfile.offline` (см. [docs/04](docs/04-сервер-и-эксплуатация.md)).

## Быстрый старт без Docker (Windows, PowerShell)

```powershell
cd afisha
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

copy .env.example .env                       # при желании впишите ключи
.\.venv\Scripts\python.exe -m app.ingest data\sample_events.json   # 120 реальных событий для первого запуска
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
```

Откройте <http://localhost:8000>: сайт, <http://localhost:8000/docs>: API, <http://localhost:8000/widget-demo>: виджет.

Бот (нужен токен от @BotFather в `TELEGRAM_BOT_TOKEN`):

```powershell
.\.venv\Scripts\python.exe -m app.bot
```

Пользоваться ботом можно только после подписки на канал `REQUIRED_CHANNEL` (по умолчанию [@sz_orenteam](https://t.me/sz_orenteam)).
Остальным бот присылает приглашение с кнопками «Подписаться» и «Я подписался». Чтобы Telegram показывал боту список
подписчиков, **бота нужно назначить администратором канала** (достаточно минимальных прав): иначе проверить подписку
нельзя, и бот никого не пропускает. При запуске в лог пишется, доступна ли проверка. Пустой `REQUIRED_CHANNEL` отключает условие.

Тесты: `pip install -r requirements-dev.txt`, затем `python -m pytest`.

Стили фронтенда собирает Tailwind CSS (нужен Node, только разработчику): `npm install`, затем `npm run build:css`. Готовый `app/static/tailwind.css` лежит в репозитории, поэтому на сервере сборка не нужна.

## ИИ-агент

Агент работает в двух режимах с одним интерфейсом (`agent.ask`), на сайте и в боте видно, какой из них ответил.

* **llm** (есть `GEMINI_API_KEY`, ключ берётся в [Google AI Studio](https://aistudio.google.com/apikey)): Google Gemini
  получает два инструмента, `search_events` и `get_event`, которые ходят в нашу БД. Он сам переводит «в субботу», «с ребёнком»,
  «до 1000» в параметры поиска, при слишком общем вопросе задаёт один уточняющий вопрос, при пустой выдаче ослабляет условия
  и говорит об этом. Рекомендует он только события, которые реально вернул поиск: `event_ids` в ответе проверяются на стороне
  сервера, выдуманные отбрасываются. Описания событий приходят из внешних источников, поэтому в промпте они объявлены
  данными, а не инструкциями. Модель задаётся `GEMINI_MODEL` (по умолчанию `gemini-3.5-flash`; список доступных вашему ключу
  моделей можно получить через `client.models.list()`).
* **rules** (нет ключа, сеть недоступна, модель заблокировала запрос или вернула ошибку): запрос разбирается регулярками
  (`app/rules.py`): даты («в субботу», «на выходных», «15 ноября»), цена, возраст ребёнка, город, категория. Демо не падает
  без интернета.

В интерфейсе под ответом видно, кто отвечал. Google API доступен не из всех регионов: если из вашего он закрыт, запросы нужно
пускать через прокси (`HTTPS_PROXY` в окружении).

Переключатель режима: `AGENT_MODE=auto|llm|rules` (`rules`: никогда не вызывать модель). `POST /api/ask` ограничен 20 запросами
в минуту с IP, а у вызовов модели есть общий бюджет (см. раздел «Безопасность»).

## API

```bash
# Поиск: бесплатные детские события на выходных в Уфе
curl "http://localhost:8000/api/events?when=weekend&city=Уфа&kids=true&free=true"

# Фильтры: q, city, category, when|date_from|date_to, price_max, free, age, kids, status, sort, limit, offset
curl "http://localhost:8000/api/events?category=theatre&price_max=1500&age=12"

# Вопрос обычным языком (history — прошлые реплики для уточнений)
curl -X POST http://localhost:8000/api/ask -H "Content-Type: application/json" \
     -d '{"message": "куда пойти в субботу с ребёнком до 1000 рублей"}'

# Приём события от организатора или сайта министерства (нужен ADMIN_API_KEY в .env)
curl -X POST http://localhost:8000/api/events -H "X-API-Key: <ключ>" -H "Content-Type: application/json" \
     -d '{"title": "Концерт", "start_at": "2026-11-14T19:00:00+05:00", "city": "Уфа", "price_min": 300, "source": "example.ru"}'
```

Остальное: `GET /api/events/{id}`, `GET /api/meta` (города и категории для фильтров), `POST /api/events/bulk`,
`PATCH /api/events/{id}/status` (отмена, перенос, аншлаг). Даты в API: местное время Уфы (UTC+5), с часовым поясом
или без. Ответ `GET /api/events`: `{items, total, limit, offset}`.

## Безопасность

Чтение афиши открыто всем, поэтому защита строится вокруг трёх вещей: данные нельзя испортить, сервис нельзя положить,
платную модель нельзя сжечь.

* **Приём данных.** Только с заголовком `X-API-Key`; ключ короче 24 символов не принимается вовсе, сравнение идёт за
  постоянное время, после 10 неудачных попыток адрес минуту не обслуживается. Ссылки события проходят только с `http(s)://`
  (никаких `javascript:`), у всех полей есть предел длины, у цен и возраста пределы значений.
* **Чужие сайты.** CORS открывает другим сайтам только `GET`. Запрос `POST`/`PATCH` из браузера с чужого сайта отклоняется
  (403) по заголовкам `Origin` и `Sec-Fetch-Site`: посторонняя страница не может тратить квоту ИИ руками своих посетителей.
* **Лимиты.** 300 запросов в минуту на адрес ко всему API, 20 в минуту к `/api/ask`, в боте 8 вопросов в минуту и один
  одновременно на пользователя. IPv6 считается подсетью /64. Тело запроса не больше 1 МБ (пачка событий до 5 МБ),
  поиск не длиннее 200 символов и 8 слов.
* **Бюджет ИИ.** К модели одновременно идёт не больше `LLM_MAX_CONCURRENCY` запросов, за сутки не больше `LLM_DAILY_LIMIT`,
  на один ответ не больше `LLM_TIME_BUDGET` секунд. Сверх бюджета отвечает режим правил: сервис не копит очередь и не падает.
  История диалога приходит от клиента, поэтому в модель уходит только её хвост (10 реплик по 2000 символов).
* **Заголовки.** `Content-Security-Policy` (скрипты только свои и Telegram, встроенные запрещены, во фрейме страницу
  открывает только Telegram), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS по HTTPS.
* **Модель и данные источников.** Модель получает только инструменты чтения. Тексты из источников объявлены ей данными,
  а не инструкциями; рекомендовать она может только события, которые вернул поиск; её ответ везде экранируется.
* **Бот.** Данные кнопок разбираются строго (их может подделать клиент), названия из источников экранируются,
  сообщения без автора (от имени канала) подписку не проходят.
* **Развёртывание.** `deploy/run.sh` запускает контейнеры не от root, с файловой системой только для чтения, без
  возможностей ядра и с потолком памяти; `deploy/nginx-afisha.conf` добавляет лимиты запросов и скрывает версию сервера.
  Секреты лежат в `.env` с правами 600 и в образ не попадают. Версии зависимостей закреплены в `requirements.txt`.

Чего нет: входа пользователей и ролей (админ-методы под одним общим ключом), защиты сайта подпиской (она действует только
в боте), а лимиты и состояние живут в памяти одного процесса: при нескольких экземплярах их нужно вынести в Redis.

## Дедупликация и статусы

Событие считается дублем, если совпадает город и день, время начала отличается не более чем на 3 часа (дневной и вечерний
сеанс остаются разными), а заголовки похожи после нормализации (без кавычек и слов «спектакль/концерт/…»; «Лебединое озеро»
и «Лебединое озеро. Балет П. И. Чайковского» склеиваются, а «Лекция 1» и «Лекция 2» нет). Событие с тем же `url`
обновляется на месте, даже если дата перенесена. При слиянии берётся более полное описание, цены расходящихся
источников показываются диапазоном, а при конфликте статусов побеждает самый «тревожный»: отмена важнее, чем «состоится».

## Источники данных и проверка на дубликаты

Подключено пять источников и общий механизм для любых сайтов с разметкой schema.org. Один запуск:

```powershell
.\.venv\Scripts\python.exe -m app.sync all --dry-run          # что загрузится (ничего не записывая)
.\.venv\Scripts\python.exe -m app.sync all --limit 150        # все источники подряд; сбой одного не останавливает остальные
.\.venv\Scripts\python.exe -m app.sync yandex-afisha --limit 200 --cities ufa,sterlitamak
.\.venv\Scripts\python.exe -m app.dedup_audit                 # похожие пары, оставшиеся после склейки
.\.venv\Scripts\python.exe -m app.dedup_audit --apply         # слить уверенные пары
```

| Источник | Как берём | Что даёт |
|---|---|---|
| `culture-ru` | JSON страницы афиши | федеральная афиша учреждений культуры, ближайший сеанс |
| `yandex-afisha` | страницы событий по sitemap.xml: schema.org + расписание из состояния страницы | сеансы по датам, цена, возраст, площадка с адресом, статус отмены |
| `kassir` | разделы афиши города: schema.org | концерты, театр, шоу, детям, спорт, музеи; цена, площадка |
| `kudago` | официальный открытый API | описание, цена, возраст, категории (из России сайт бывает недоступен) |
| `sites` | любой сайт из `data/sources.json` со schema.org | театры, филармонии, площадки: без правки кода |

Одно событие из разных источников склеивается автоматически (город, день, близкое время и похожее название), у карточки видно число подтвердивших
источников, а цены расходящихся источников показываются диапазоном. После загрузки выводится сводка: сколько записей создано, сколько склеено с уже
известными и сколько из них **подтверждено другим источником**. `app.dedup_audit` дополнительно ищет пары, которые не склеились из-за разных названий
(порог мягче, 0,6), и по `--apply` сливает уверенные (от 0,72); события, которые один и тот же источник считает разными, не сливаются никогда.

Все источники ходят через общий загрузчик (`app/sources/base.py`): читается `robots.txt` (запрещено или не прочитался, страница не загружается),
между запросами пауза, только HTTPS и только разрешённые хосты, ответ не больше 8 МБ, **капчу, 403 и 429 мы не обходим** (обход просто прекращается).
Билетный сервис Ticketland отвечает ботам 403, поэтому не подключён. Условия использования данных каждого сайта стоит уточнить до публичного запуска.

Свой сайт добавляется без кода, файлом `data/sources.json` (формат и параметры `follow`/`tz_mode` описаны в `app/sources/sites.py`).

## Подробнее про culture.ru

Федеральная афиша [culture.ru](https://www.culture.ru/afisha/respublika-bashkortostan)
по Башкортостану (события публикуют сами учреждения культуры):

```powershell
.\.venv\Scripts\python.exe -m app.sync culture-ru --dry-run             # посмотреть, что загрузится
.\.venv\Scripts\python.exe -m app.sync culture-ru --pages 10            # ~200 ближайших событий (20 на страницу)
.\.venv\Scripts\python.exe -m app.sync culture-ru --pages 10 --drop-demo  # то же, но без выдуманных демо-событий
```

Повторный запуск безопасен: события обновляются по ссылке, а не дублируются. Для регулярного обновления поставьте команду в
планировщик задач, например раз в несколько часов.

Как устроен обход (`app/sources/culture_ru.py`): данные берутся из JSON, встроенного в страницу афиши (`__NEXT_DATA__`),
без обхода закрытых разделов. Перед запуском читается `robots.txt` (если запрещено или не прочитался, обход не начинается),
между страницами пауза 1,5 с, запросы идут с User-Agent `bashafisha-hackathon`. Время событий приходит в UTC и переводится в Уфу.

Что важно знать об источнике:
* в карточке только **ближайший сеанс**, а не всё расписание;
* **статусов** (отмена, перенос) и **описаний** в списке нет, поэтому поля пустые: ничего не выдумываем;
* у постоянных выставок есть только дата окончания, началом считаем день синхронизации;
* у некоторых событий в качестве города указан район («Гафурийский район»);
* адаптер ходит **напрямую, в обход системного прокси** (российский сайт через зарубежный прокси недоступен);
  чтобы использовать прокси из окружения, задайте `AFISHA_USE_PROXY=1`;
* формат страницы может измениться: тогда синхронизация остановится с понятной ошибкой, а не загрузит мусор.
  Условия использования данных culture.ru стоит уточнить до публичного запуска.

## Загрузка из файлов

```powershell
.\.venv\Scripts\python.exe -m app.ingest events.json    # или events.csv
```

Формат записи: `title`, `start_at`, `source` (обязательны), далее `description`, `category`, `city`, `venue`, `address`,
`end_at`, `price_min`, `price_max` (0 = бесплатно, пусто = неизвестно), `age_limit` (`12` или `"12+"`), `kids_friendly`,
`url`, `image_url`, `status`. Любой новый источник (сайт театра, музея) пишется как адаптер, который собирает записи в этом формате
(образец: `app/sources/culture_ru.py`), остальное (нормализация, дедупликация, статусы) уже сделано.

## Тестовые данные

Сервис не показывает выдуманных событий: первый запуск использует `data/sample_events.json` (реальные афиши, источник записан у
каждой записи; пересоздать выгрузку из своей базы: `python scripts/export_sample.py`).

Выдуманные события нужны только автотестам и лежат в `tests/demo_data.py`, в образ они не попадают. Если такие события всё же
попали в локальную базу (`python -m tests.demo_data`), интерфейс, бот и виджет помечают их значком «демо», а
`python -m app.maintenance demo-reset --apply` удаляет только их, реальные не трогает.

## Виджет

```html
<div id="afisha"></div>
<script src="https://ВАШ-СЕРВЕР/widget.js" data-target="#afisha" data-when="weekend" data-limit="5"></script>
```

Рисуется в Shadow DOM, поэтому стили сайта не ломают виджет, а виджет не ломает стили сайта.

## Устройство

```
источники ──► ingest (нормализация → дедупликация) ──► БД (SQLite / PostgreSQL через DATABASE_URL)
                                                          │
                        search.py (один поиск на всех) ◄──┤
                           ▲        ▲        ▲            │
                    REST API   ИИ-агент   Telegram-бот    └─► сайт, виджет
```

  Автоматического расписания синхронизации нет, и события, пропавшие из источника, сами не удаляются и не помечаются отменёнными.
* Живой вызов Gemini не проверялся (в окружении разработки не было ключа): ответы агента проверены тестами с подменой
  клиента на реальных типах SDK. Бот проверен тестами и запущен в Telegram.
* PostgreSQL не проверялся (код написан на SQLAlchemy, поиск по тексту использует только `LIKE`).
* Состояние бота (выбранный город, история диалога) и лимитер запросов живут в памяти процесса.
* Админ-методы защищены одним общим ключом; ролей и аккаунтов организаторов нет.
* Резервной модели нет: при блокировке запроса, лимитах или недоступности Gemini агент отвечает по правилам.
