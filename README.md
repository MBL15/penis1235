# Афиша культуры Башкортостана

Единая достоверная афиша культурных событий республики: **веб-сервис + Telegram-бот + открытый REST API + ИИ-агент**.
События из разных источников склеиваются без дублей, у каждого есть статус (состоится, перенесено, отменено, билеты проданы),
а запрос обычным языком («куда пойти в субботу с ребёнком до 1000 рублей») превращается в подборку с объяснением.

> **База знаний проекта:** [docs/README.md](docs/README.md): архитектура, запуск, выкладка на сервер и эксплуатация, безопасность, решения и грабли.

> **Неофициальный сервис.** Проект не является сервисом Министерства культуры Республики Башкортостан и не связан с ним.
> Данные собраны из открытых источников (culture.ru, Яндекс Афиша, Kassir.ru), перед визитом их нужно уточнять у организатора.
> Эта пометка показывается на сайте, в боте, в виджете и в описании API.

## Выбранный уровень решения

**Уровень 2 «Сайт»** по ТЗ (§5): Telegram-бот, веб-каталог, REST API и виджет. Уровни кумулятивные, поэтому сюда входят и
требования уровня 1.

**Уровень 3 «Агент» пока не заявляется.** Реализовано: трасса каждого ответа, подсчёт токенов и стоимости, шесть
инструментов с лимитом пять вызовов на ответ, подтверждение действий человеком, защита от инъекций, проверка фактов в ответе
модели (числа и названия без основания пользователю не показываются), лимиты расхода модели на диалог и на пользователя в
сутки, режим правил с теми же фильтрами, набор из 60 контрольных запросов с поиском по ключевым словам как базовой линией
и 10 отложенных запросов (`eval/`). Режим правил проходит все пороги §9.2 уровня 3.

**Прогон на модели** (`gemini-3.5-flash-lite`, 13.11.2026 20:47, `eval/reports/2026-11-13-llm-3.5-flash-lite.md`): модель ответила
на 50 запросов из 60, задержка p95 **5,5 с** (порог 8 с), фактическая точность 100 %, выдуманных событий 0, инъекции 0 выполнений
и 0 утечек. **Не выполнены 2 порога:** выполнение ограничений 53 % (порог 80 %) и честный отказ 50 % (порог 100 %). После прогона
исправлено: все 4 «нечестных отказа» оказались честными ответами, которые проверка не узнавала («сейчас нет в нашей афише»), —
словарь проверки расширен; если модель называет события, но не возвращает их id (главная причина пустой выдачи), сервер один раз
просит указать `event_ids`. Объявлять уровень 3 стоит после повторного прогона, 10 внешних запросов и расчёта стоимости.

Для уровня 2 закрыто (подробности и номера пунктов ТЗ: [upd.md](upd.md)): страница события с постоянной ссылкой, API с версией
в адресе, единый формат ошибок, кеширование, метрики, структурные логи с идентификатором запроса, админ-интерфейс с журналом
изменений, форма обратной связи с защитой от спама, статусы «опубликовано/черновик/отменено», сырые данные источников,
справочник площадок с синонимами (`data/venues.json`), миграции схемы (Alembic), подписки в REST API (из Telegram Mini App),
высота виджета, подсказка к пустой выдаче, возраст «не указан» отдельно от «0+».

Из уровня 4 уже сделано без ИИ: проверка карточек перед публикацией с очередью модерации, сбор по расписанию с пометкой пропавших
событий, планировщик «Выходной день» (см. разделы ниже). Не сделано из уровня 4: качество сбора на 50 карточках, проверенных вручную.

Для уровня 2 ещё не закрыто: коллекция запросов для Postman и примеры ответов в OpenAPI, замеры метрик качества из §9.1 ТЗ
(полнота карточек, полнота поиска, пустая выдача), проверка доступности (контраст, клавиатура, 360 px), запись демо и краткая
записка о решении. Аккаунты и роли из ТЗ §3 сделаны (вход через Telegram, кабинет, история по согласию, роли, ключи Министерства): [docs/08](docs/08-аккаунты-и-роли.md); вход кнопкой на сайте живьём не проверялся.

## Запуск одной командой (Docker)

```bash
docker compose up --build            # сайт и API: http://localhost:8000, документация: /docs
docker compose --profile bot up --build   # то же и Telegram-бот (нужен TELEGRAM_BOT_TOKEN в .env)
docker compose --profile sync up --build  # сбор по расписанию (data/schedule.json); источники должны открываться с этой машины
```

Нужен только Docker. Файл `.env` необязателен: без него работают сайт, API и режим «без ИИ» (образец: `.env.example`).
При первом запуске подгружается `data/sample_events.json`: 140 записей (118 событий) из трёх открытых афиш на 13.11.2026 (источник
записан у каждого, повторная загрузка дублей не создаёт). Отключить: `LOAD_SAMPLE_DATA=0`. База хранится в томе
`afisha-data`, порт меняется переменной `WEB_PORT`. Образ строится из PyPI; на сервере без доступа к PyPI используется
`deploy/Dockerfile.offline` (см. [docs/04](docs/04-сервер-и-эксплуатация.md)).

## Быстрый старт без Docker (Windows, PowerShell)

```powershell
cd afisha
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

copy .env.example .env                       # при желании впишите ключи
.\.venv\Scripts\python.exe -m app.ingest data\sample_events.json   # 140 записей (118 событий) для первого запуска
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
```

Откройте <http://localhost:8000>: сайт, <http://localhost:8000/docs>: API, <http://localhost:8000/widget-demo>: виджет.

Бот (нужен токен от @BotFather в `TELEGRAM_BOT_TOKEN`):

```powershell
.\.venv\Scripts\python.exe -m app.bot
```

Обязательная подписка на канал по умолчанию **выключена** (в ТЗ такого условия нет). Чтобы включить, задайте `REQUIRED_CHANNEL=@sz_orenteam`
([канал](https://t.me/sz_orenteam)): тогда остальным бот присылает приглашение с кнопками «Подписаться» и «Я подписался». Чтобы Telegram показывал боту список
подписчиков, **бота нужно назначить администратором канала** (достаточно минимальных прав): иначе проверить подписку
нельзя, и бот никого не пропускает. При запуске в лог пишется, доступна ли проверка. Пустой `REQUIRED_CHANNEL` (значение по умолчанию) отключает условие.

Тесты: `pip install -r requirements-dev.txt`, затем `python -m pytest` (651 тест, около 45 секунд; в сеть и к платной модели не ходят).

### MCP-сервер

`python -m app.mcp_server` отдаёт инструменты афиши внешним ИИ-клиентам (Claude Desktop, Claude Code, IDE) по протоколу
Model Context Protocol через stdio. Только чтение: `search_events`, `get_event`, `find_similar`, `get_venue_schedule`
(те же, что у агента), `list_facets` (города и категории) и `plan_day` (планировщик «Выходной день»). Подписки и обращения
не вынесены: они меняют данные и требуют подтверждения человеком. База та же, что у сервиса (`DATABASE_URL` или `afisha.db`).
Подключение клиента (путь к Python из своего окружения):

```json
{"mcpServers": {"afisha": {"command": "python", "args": ["-m", "app.mcp_server"], "cwd": "/путь/к/репозиторию"}}}
```

Стили фронтенда собирает Tailwind CSS (нужен Node, только разработчику): `npm install`, затем `npm run build:css`. Готовый `app/static/tailwind.css` лежит в репозитории, поэтому на сервере сборка не нужна.

## Подписки на новые события (бот)

* `/subscribe`: выбор города (или «Вся республика») и категории (или «Любая»), до 10 подписок на чат; `/subscriptions`: список
  с удалением по одной; **`/unsubscribe`: отписка от всех одной командой**; `/cancel`: отменить начатое оформление.
* Чтобы не быть навязчивым, бот пишет **не чаще одного раза в сутки**, только с 9:00 до 21:00 по Уфе, присылает не больше пяти
  событий (остальные считает числом) и только те, что появились в афише после подписки.
* **Какие данные хранятся:** номер чата Telegram и выбранные город и категория (таблица `subscriptions`), больше ничего.
  **Срок хранения:** до отписки, но не дольше 12 месяцев с момента оформления; при блокировке бота подписка удаляется сразу.
  Рассылку выполняет процесс бота (проверка каждые 30 минут).

## ИИ-агент

Агент работает в двух режимах с одним интерфейсом (`agent.ask`); на сайте и в боте под ответом видно, какой из них ответил.

* **llm** (есть `GEMINI_API_KEY`, ключ берётся в [Google AI Studio](https://aistudio.google.com/apikey)): Google Gemini
  получает шесть инструментов по нашей БД, не больше пяти вызовов на ответ: `search_events` (дата, время начала и окончания,
  длительность, язык, площадка, цена, возраст, статус), `get_event`, `find_similar`, `get_venue_schedule`, `subscribe`,
  `save_feedback`. Он сам переводит «в субботу», «с ребёнком», «до 1000» в параметры поиска, при слишком общем вопросе задаёт
  один уточняющий вопрос, при пустой выдаче называет мешающее условие. Каждое событие объясняет в 1–2 предложения.
  Рекомендует только то, что реально вернул поиск: `event_ids` проверяются сервером, выдуманные отбрасываются. Модель
  задаётся `GEMINI_MODEL` (по умолчанию `gemini-3.5-flash-lite`; список доступных вашему ключу моделей даёт `client.models.list()`). Если основная модель вернула 429 (исчерпана квота, а у каждой
  модели Gemini она своя), 503 (перегрузка) или 404, берётся следующая из `GEMINI_FALLBACK_MODELS` (по умолчанию
  `gemini-3.1-flash-lite`, `gemini-3.6-flash`, `gemini-3.8-flash`, `gemini-4-hydrogen`); отказавшая модель 10 минут не трогается. Какая модель ответила, видно в
  трассе (поле модели и флаг `model_skipped`). Запасные модели легче, поэтому качество ответов нужно проверять прогоном `eval`.
* **rules** (нет ключа, сеть недоступна, модель заблокировала запрос или вернула ошибку, исчерпан бюджет): запрос разбирается
  правилами (`app/rules.py`): даты («в субботу», «на выходных», «15 ноября», «в декабре»), время («вечером», «после 19:00»,
  «закончится не позже 22:00»), длительность, язык, цена («до 1000», «2000 на двоих»), возраст и «с детьми», город и категория
  с исправлением опечаток, слова из запроса («джаз», «Земфира»: ищутся в названиях и описаниях, и если не нашлись, это сказано
  прямо), уточнения («ещё», «подешевле», «в другой день», «что-нибудь похожее»). Если условия вместе невыполнимы, названо
  одно мешающее и сказано, что ослаблено. Чего агент не умеет (расстояние, дорога), он говорит прямо.
* **Трасса каждого ответа** (ТЗ §7.4): запрос, как он понят, вызовы инструментов с аргументами, найденные события,
  задержка, токены, стоимость. Ссылка «Как получен ответ» под ответом на сайте и в боте (в боте при HTTPS-адресе),
  `GET /api/v1/traces/{id}`, список для модератора `GET /api/v1/admin/traces`. Хранится 30 дней; в трассе текст вопроса,
  но нет адреса и номера чата.
* **Действия, меняющие данные** (подписка, перенос подписки, заявка): агент их только предлагает. Выполняет человек кнопкой
  «Подтвердить» (сайт, бот) или `POST /api/v1/agent/actions/{id}/confirm`; предложение живёт 15 минут. Подписки привязаны к
  чату Telegram и подтверждаются в нём. Пока кнопка не нажата, ничего не меняется.
* **Защита** (`app/safety.py`): просьбы раскрыть инструкции или сменить роль отклоняются до обращения к модели; в описаниях
  событий (внешние данные) фразы, похожие на приказы, вырезаются, и описание остаётся данными; в системном промпте лежит
  метка-ловушка, и если она появилась в ответе, ответ заменяется отказом; вопросы не про афишу получают короткий ответ без
  обращения к модели. **Проверка фактов** (ТЗ §7.1): числа (цены, даты, время, возраст) и названия в «ёлочках», которых нет в
  результатах инструментов и в словах самого пользователя, пользователю не показываются: если события найдены, текст модели
  заменяется ответом из полей базы, если нет — отвечает режим правил; в трассе флаги `ungrounded_numbers`, `ungrounded_titles`,
  `reply_replaced`. Реплики «ассистента» из истории, которую присылает клиент, основанием для фактов не считаются.

В интерфейсе под ответом видно, кто отвечал. Google API доступен не из всех регионов: если из вашего он закрыт, запросы нужно
пускать через прокси (`HTTPS_PROXY` в окружении).

Переключатель режима: `AGENT_MODE=auto|llm|rules` (`rules`: никогда не вызывать модель). `POST /api/ask` ограничен 20 запросами
в минуту с IP, а у вызовов модели есть общий бюджет (см. раздел «Безопасность»).

**Лимиты расхода модели на человека** (ТЗ §6.5), в токенах (вход + выход): `LLM_DIALOG_TOKENS` на диалог (по умолчанию 60 000,
около 8 ответов модели; диалог — вопросы за последние `LLM_DIALOG_WINDOW_MIN` = 30 минут, границу определяет сервер, а не
присланная клиентом история) и `LLM_USER_DAILY_TOKENS` на сутки (по умолчанию 150 000, около 20 ответов). Человек — чат Telegram
(в боте и после входа на сайте, счёт общий) или адрес посетителя. Сверх лимита отвечает режим правил с пояснением, почему.
Счётчики живут в памяти процесса. Стоимость в рублях — те же токены по формуле ниже.

### Стоимость ответа

```
стоимость ответа, ₽ = (входные токены × тариф_вход + выходные токены × тариф_выход) / 1 000 000
стоимость диалога   = сумма по его ответам; в режиме правил 0 ₽, модель не вызывается
```

Токены сервер берёт из `usage_metadata` ответа Gemini (входные: `prompt_token_count`; выходные: `candidates_token_count`
плюс `thoughts_token_count`, размышления оплачиваются как выходные) и суммирует по всем шагам ответа. Тариф в код не зашит:
он задаётся в `.env` как `LLM_PRICE_INPUT_RUB_PER_M` и `LLM_PRICE_OUTPUT_RUB_PER_M` (рублей за миллион токенов, уже по курсу
вашего аккаунта). **Без тарифа токены считаются, а рубли нет**: в трассе и в отчёте прогона так и написано.

Пример: **условный** тариф 10 ₽ за миллион входных и 40 ₽ за миллион выходных токенов (цифры для примера, подставьте тариф
своего аккаунта). Единственный живой ответ, который удалось увидеть (проверка чата в браузере: два вызова инструментов,
в базе 650 событий), занял 8 911 входных и 2 303 выходных токена: (8 911 × 10 + 2 303 × 40) / 1 000 000 = **0,18 ₽**.
Порог уровня 3, среднее не больше 5 ₽ на диалог, при такой стоимости позволяет около 27 таких ответов.

**Среднее по прогону набора** (`gemini-3.5-flash-lite`, 13.11.2026, 50 ответов модели): **7 002 входных и 237 выходных токенов на
ответ**. По тому же условному тарифу: (7 002 × 10 + 237 × 40) / 1 000 000 ≈ **0,08 ₽ за ответ**; диалог из 5 ответов ≈ 0,4 ₽. Модели
Gemini, которые использует сервис, на бесплатном тарифе AI Studio стоят 0 ₽ (ограничены квотой запросов в сутки). Для отчёта в
рублях задайте `LLM_PRICE_*` по своему тарифу и повторите прогон.

## Контрольные запросы и метрики качества

Папка `eval/` (подробности в [eval/README.md](eval/README.md)): 60 запросов (подборки с тремя и более условиями, опечатки,

```bash
python -m eval.run --mode rules                       # без ключа и сети, отчёт в eval/reports/
python -m eval.run --mode llm --confirm-spend         # настоящая модель: тратит квоту и деньги
python -m eval.run --queries путь/к/внешним.json      # внешние запросы проверяющего
```

модели. Первый прогон до исправлений дал 29 из 60, отложенная выборка при первом прогоне 7 из 10 (ограничения 25 %): найденные
дефекты разобраны в [upd.md](upd.md) и [eval/README.md](eval/README.md).

## Сбор по расписанию и проверка карточек

Сбор без ручного запуска (ТЗ §6.5, §14): `python -m app.scheduler` читает `data/schedule.json` и запускает задачи, которым пора.
В расписании по умолчанию: culture.ru и Яндекс Афиша раз в сутки, Kassir.ru раз в 12 часов, перепроверка опубликованных событий раз
в 6 часов. Новый источник добавляется строкой в файл, код менять не нужно.

* **Проверка перед публикацией** (`app/verify.py`, без ИИ): новое событие из источника сначала попадает в очередь модерации, потом
  проверяется: ссылка источника открывается (с защитой от запросов во внутреннюю сеть, в том числе через подмену DNS: соединение
  идёт только с проверенным IP, прокси из окружения не используется, вернуть его можно `AFISHA_USE_PROXY=1`), дата в будущем, не дубль. Каждая карточка
  получает `verified_at` и `confidence` (0–1: ссылка 0,35, дата 0,20, полнота до 0,20, источники до 0,15, не дубль 0,10).
  Уверенность не ниже 0,55 и нет блокирующих причин: событие публикуется; иначе остаётся в очереди с причиной в `review_reason`.
* **Пропавшие из источника события**: после полного прохода события, которых источник больше не присылает, получают отметку, а если
  пропали у всех своих источников, уходят в очередь модерации («пропало: …»). Решает человек. Если источник присылает событие снова,
  оно возвращается в выдачу. От ложных срабатываний: пустой ответ и проход, где записей меньше половины прежнего, ничего не помечают.
  Включается `"mark_vanished": true` у задачи.
* Запуски пишутся в таблицу `sync_runs`; вкладка «Сбор» в админке и `GET /api/v1/admin/sync-runs`.

```bash
python -m app.scheduler --list         # расписание и последние запуски
python -m app.scheduler --once         # запустить то, что пора, и выйти (cron, Планировщик заданий Windows)
python -m app.scheduler --run kassir   # запустить задачу сейчас
python -m app.scheduler                # работать постоянно (docker compose --profile sync up)
python -m app.verify run --no-links    # только проверить карточки (--all: все будущие события)
```

Пределы: сайты источников доступны не с каждого сервера (с российского сервера culture.ru отвечает отказом), поэтому планировщик
запускают там, откуда они открываются. Проверка ссылки не видит «мягких» ошибок: Kassir.ru на несуществующую страницу отвечает 200, а
culture.ru роботам отвечает 425, и такая ссылка считается «не подтверждённой», а не «битой».

## Планировщик «Выходной день»

`/plan` на сайте, `POST /api/v1/plan` и команда `/plan` в боте собирают из афиши 2–4 события одного дня без пересечений по времени:
с запасом 10 минут и оценкой дороги между площадками (по координатам или 20 минут по городу), стоимостью на всех и объяснением,
что изменить, если ограничения несовместимы (поднять бюджет, расширить окно, разрешить дорогу подольше). Модель не вызывается.

* **День по умолчанию** (если не назван): ближайшая суббота, причём в субботу до 18:00 это сегодня, позже следующая. Так же
  понимается слово «суббота», сказанное в субботу.
* В план на сегодня не попадают уже начавшиеся события; выставки и экскурсии «на период» без часов работы не попадают никогда.
* Бот разбирает условия из текста: `/plan 2000 рублей на двоих, суббота, Уфа, ребёнок 8 лет, с 12 до 20, дорога до 30 минут`.

## API

Версия в адресе: **`/api/v1`**. Пути без версии (`/api/events` и т. д.) работают так же и оставлены для совместимости виджетов.
Документация и примеры: `/docs` (Swagger), `/openapi.json` (OpenAPI 3.1).

```bash
# Поиск: бесплатные детские события на выходных в Уфе
curl "http://localhost:8000/api/v1/events?when=weekend&city=Уфа&kids=true&free=true"

# Фильтры: q, city, venue, category, when|date_from|date_to, time_from, time_to, ends_by, max_duration, language,
#          price_max, free, age, kids, status, sort, limit, offset
curl "http://localhost:8000/api/v1/events?category=theatre&price_max=1500&age=12"

# Справочники для фильтров: города, категории, площадки (название из /venues подставляется в venue=)
curl "http://localhost:8000/api/v1/cities"
curl "http://localhost:8000/api/v1/venues?city=Уфа"

# Карточка одного события (отменённое тоже доступно, у него status=cancelled)
curl "http://localhost:8000/api/v1/events/42"

# Вопрос обычным языком (history — прошлые реплики, context_event_ids — события прошлого ответа для «ещё» и «похожее»)
curl -X POST http://localhost:8000/api/v1/ask -H "Content-Type: application/json" \
     -d '{"message": "куда пойти в субботу с ребёнком до 1000 рублей"}'

# Как получен ответ: трасса по trace_id из ответа; действие, которое предложил агент, подтверждается отдельным вызовом
curl "http://localhost:8000/api/v1/traces/<trace_id>"
curl -X POST "http://localhost:8000/api/v1/agent/actions/<id>/confirm"

# Приём события от организатора или сайта министерства (нужен ключ: ADMIN_API_KEY или ADMIN_USERS в .env)
curl -X POST http://localhost:8000/api/v1/events -H "X-API-Key: <ключ>" -H "Content-Type: application/json" \
     -d '{"title": "Концерт", "start_at": "2026-11-14T19:00:00+05:00", "city": "Уфа", "price_min": 300, "source": "example.ru"}'

# Пачка событий: плохая запись не отклоняет остальные, в ответе rejected с причинами
curl -X POST "http://localhost:8000/api/v1/events/bulk?publish=false" -H "X-API-Key: <ключ>" -H "Content-Type: application/json" \
     -d @events.json
```

Остальное: `GET /api/v1/meta`, `GET /api/v1/categories`, `PATCH /api/v1/events/{id}/status` (отмена, перенос, аншлаг),
`POST /api/v1/feedback` и `GET /api/v1/feedback/form`, `GET /api/v1/health` и `/health`, методы модератора `/api/v1/admin/*`.
Даты в API: местное время Уфы (UTC+5), с часовым поясом или без. Ответ `GET /api/v1/events`: `{items, total, limit, offset}`.

**Единый формат ошибок** (все методы, по-русски):

```json
{"error": {"code": "validation_error", "message": "Некорректные параметры запроса",
           "details": [{"field": "limit", "message": "не больше 100"}], "request_id": "9f1c0b7e5d3a4c2e8b6a1d0f3e5c7a92"}}
```

Коды: `bad_request`, `unauthorized`, `forbidden`, `not_found`, `method_not_allowed`, `payload_too_large`, `validation_error`,
`rate_limited` (с заголовком `Retry-After`), `unavailable`, `internal_error`. Идентификатор запроса всегда в заголовке
`X-Request-ID`: его можно передать самому (буквы, цифры, `._-`, 8–64 символа), он же попадёт в логи.

**Кеширование:** ответы справочников, карточки, списка и страницы `/event/{id}` приходят с `ETag` и `Cache-Control: public`
(карточка 60 с, список 30 с, справочники 5 мин); повторный запрос с `If-None-Match` получает `304` без тела.

## Администрирование и журнал изменений

Страница **`/admin`**: вход по ключу (хранится только в открытой вкладке), очередь модерации (черновики), все события, правка
и создание карточки, снятие с публикации, смена статуса, импорт JSON/CSV с отчётом «создано, обновлено, без изменений,
отклонено и почему», журнал изменений, обращения из формы. Те же действия доступны методами `/api/v1/admin/*`.

* **Ключи.** Общий `ADMIN_API_KEY` (в журнале это «admin») и/или личные ключи модераторов `ADMIN_USERS=anna:ключ,boris:ключ`:
  в журнале действие записывается на имя владельца ключа. Ключ не короче 24 символов, после 10 неудачных попыток адрес на минуту
  блокируется.
* **Журнал** (`audit_log`): кто, когда и что изменил (поля «было → стало»), идентификатор запроса. Пишут создание, обновление
  источником, слияние дублей, правка модератором, смена статуса и публикации, импорт, обработка обращений.
* **Сырые данные** (`raw_records`): каждая запись источника хранится в том виде, в каком пришла (в том числе отклонённая, с
  причиной). Нормализацию можно переиграть без нового сбора: `python -m app.maintenance reprocess [--source kassir.ru] --apply`.
* **Публикация.** Новое событие по умолчанию `published`; импорт с `publish=false` (флажок «черновиками» в админке, `--draft` в
  командной строке) создаёт `draft`: черновик не виден в поиске, API, боте и у ИИ-агента, а в админке стоит в очереди модерации.
  Отмена — это `status=cancelled`: такое событие убрано из выдачи, но открывается по прямой ссылке с явной пометкой.
* **Известное ограничение.** Если источник пришлёт своё значение поля, которое модератор исправил вручную, при следующей
  синхронизации оно перезапишет правку: источник остаётся авторитетом для собственных данных.

## Обратная связь

Страница **`/feedback`** (на карточке события — «Сообщить об ошибке»): ошибка в афише, заявка организатора (добавить или
уточнить событие), вопрос. Защита от спама без капчи: скрытое поле-ловушка, подписанная сервером метка времени формы (быстрее
3 секунд и дольше 2 часов отклоняется), лимит 5 обращений в час с адреса и общий лимит, не больше двух ссылок, отсев повторов.
**Персональные данные:** контакт необязателен, адрес и данные устройства не сохраняются; обращение хранится не дольше 180 дней
(обработанное 90) и удаляется автоматически. Обращения видны модератору в `/admin` с фильтром по статусу: новые, в работе,
обработанные или все (`GET /api/v1/admin/feedback?status=new|in_progress|processed|all`); ответ модератора автору-аккаунту
приходит в Telegram.

## Логи и метрики

* **Логи**: JSON, по строке на запрос (`LOG_FORMAT=text` для разработки): время, метод, маршрут, статус, длительность, `request_id`.
  Адресов посетителей, строки запроса и текстов обращений в логах нет, access-лог uvicorn отключён. nginx пишет свой журнал без
  адресов (`deploy/nginx-afisha.conf`) и передаёт приложению тот же `X-Request-ID`.
* **Метрики** Prometheus: `GET /metrics` (запросы по методу, маршруту и статусу, ошибки 5xx, гистограмма задержки, режимы ответов
  ИИ, обращения, число событий). Снаружи закройте (`METRICS_TOKEN` или nginx), мониторинг читает с самого сервера.

## Безопасность

Чтение афиши открыто всем, поэтому защита строится вокруг трёх вещей: данные нельзя испортить, сервис нельзя положить,
платную модель нельзя сжечь.

* **Приём данных.** Только с заголовком `X-API-Key`; ключ короче 24 символов не принимается вовсе, сравнение идёт за
  постоянное время, после 10 неудачных попыток адрес минуту не обслуживается. Ссылки события проходят только с `http(s)://`
  (никаких `javascript:`), у всех полей есть предел длины, у цен и возраста пределы значений.
* **Неверный ввод даёт 4xx, а не 500.** Номера событий ограничены диапазоном базы, числа из адреса и меток разбираются только
  из ASCII-цифр («²» тоже считается цифрой в Python), обязательные поля нельзя очистить правкой. Регрессии: `tests/test_review_fixes.py`.
* **Запросы во внутреннюю сеть (SSRF).** Проверка ссылок ходит только на публичные адреса и соединяется с тем IP, который проверила
  (подмена DNS между проверкой и запросом не срабатывает); перенаправления проверяются, у сборщика источников — до перехода.
* **Чужие сайты.** CORS открывает другим сайтам только `GET`. Запрос `POST`/`PATCH` из браузера с чужого сайта отклоняется
  (403) по заголовкам `Origin` и `Sec-Fetch-Site`: посторонняя страница не может тратить квоту ИИ руками своих посетителей.
* **Лимиты.** 300 запросов в минуту на адрес ко всему API, 20 в минуту к `/api/ask`, в боте 8 вопросов в минуту и один
  одновременно на пользователя. IPv6 считается подсетью /64. Тело запроса не больше 1 МБ (пачка событий до 5 МБ),
  поиск не длиннее 200 символов и 8 слов.
* **Бюджет ИИ.** К модели одновременно идёт не больше `LLM_MAX_CONCURRENCY` запросов, за сутки не больше `LLM_DAILY_LIMIT`,
  на один ответ не больше `LLM_TIME_BUDGET` секунд. Сверх бюджета отвечает режим правил: сервис не копит очередь и не падает.
  История диалога приходит от клиента, поэтому в модель уходит только её хвост (10 реплик по 2000 символов).
* **Заголовки.** `Content-Security-Policy` (скрипты только свои и Telegram, встроенные запрещены, во фрейме страницу
  открывает только Telegram), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS по HTTPS.
* **Модель и данные источников.** Модель получает только инструменты чтения. Тексты из источников объявлены ей данными,
  а не инструкциями; рекомендовать она может только события, которые вернул поиск; её ответ везде экранируется.
* **Бот.** Данные кнопок разбираются строго (их может подделать клиент), названия из источников экранируются,
  сообщения без автора (от имени канала) подписку не проходят.
* **Развёртывание.** `deploy/run.sh` запускает контейнеры не от root, с файловой системой только для чтения, без
  возможностей ядра и с потолком памяти; `deploy/nginx-afisha.conf` добавляет лимиты запросов и скрывает версию сервера.
  Секреты лежат в `.env` с правами 600 и в образ не попадают. Версии зависимостей закреплены в `requirements.txt`.

Чего нет: разделения прав модератора на «просмотр» и «правку» (аккаунты и роли есть, [docs/08](docs/08-аккаунты-и-роли.md)),
защиты сайта подпиской (она действует только в боте), а лимиты и состояние живут в памяти одного процесса: при нескольких
экземплярах их нужно вынести в Redis. Полная модель угроз: [docs/05](docs/05-безопасность.md).

## Дедупликация и статусы

Событие считается дублем, если совпадает город и день, время начала отличается не более чем на 3 часа (дневной и вечерний
сеанс остаются разными), а заголовки похожи после нормализации (без кавычек и слов «спектакль/концерт/…»; «Лебединое озеро»
и «Лебединое озеро. Балет П. И. Чайковского» склеиваются, а «Лекция 1» и «Лекция 2» нет). Событие с тем же `url`
обновляется на месте, даже если дата перенесена. При слиянии берётся более полное описание, цены расходящихся
источников показываются диапазоном, а при конфликте статусов побеждает самый «тревожный»: отмена важнее, чем «состоится».

## Источники данных и проверка на дубликаты

Подключено пять источников и общий механизм для любых сайтов с разметкой schema.org. Один запуск:

```powershell
.\.venv\Scripts\python.exe -m app.sync all --dry-run          # что загрузится (ничего не записывая)
.\.venv\Scripts\python.exe -m app.sync all --limit 150        # все источники подряд; сбой одного не останавливает остальные
.\.venv\Scripts\python.exe -m app.sync yandex-afisha --limit 200 --cities ufa,sterlitamak
.\.venv\Scripts\python.exe -m app.dedup_audit                 # похожие пары, оставшиеся после склейки
.\.venv\Scripts\python.exe -m app.dedup_audit --apply         # слить уверенные пары
```

| Источник | Как берём | Что даёт |
|---|---|---|
| `culture-ru` | JSON страницы афиши | федеральная афиша учреждений культуры, ближайший сеанс |
| `yandex-afisha` | страницы событий по sitemap.xml: schema.org + расписание из состояния страницы | сеансы по датам, цена, возраст, площадка с адресом, статус отмены |
| `kassir` | разделы афиши города: schema.org | концерты, театр, шоу, детям, спорт, музеи; цена, площадка |
| `kudago` | официальный открытый API | описание, цена, возраст, категории (из России сайт бывает недоступен) |
| `afisha-cinema` | afisha.ru: список кинотеатров города и расписание каждого кинотеатра по дням (JSON внутри страницы) | кино: по записи на фильм, кинотеатр и день, время ближайшего сеанса и все сеансы в описании, цена от и до, возраст, длительность, постер; `--days N` дней вперёд (по умолчанию 3), города: Уфа, Стерлитамак, Нефтекамск, Октябрьский, Кумертау, Бирск, Учалы |
| `sites` | любой сайт из `data/sources.json` со schema.org | театры, филармонии, площадки: без правки кода |

Одно событие из разных источников склеивается автоматически (город, день, близкое время и похожее название), у карточки видно число подтвердивших
источников, а цены расходящихся источников показываются диапазоном. После загрузки выводится сводка: сколько записей создано, сколько склеено с уже
известными и сколько из них **подтверждено другим источником**. `app.dedup_audit` дополнительно ищет пары, которые не склеились из-за разных названий
(порог мягче, 0,6), и по `--apply` сливает уверенные (от 0,72); события, которые один и тот же источник считает разными, не сливаются никогда.

Все источники ходят через общий загрузчик (`app/sources/base.py`): читается `robots.txt` (запрещено или не прочитался, страница не загружается),
между запросами пауза, только HTTPS и только разрешённые хосты, ответ не больше 8 МБ, **капчу, 403 и 429 мы не обходим** (обход просто прекращается).
Билетный сервис Ticketland отвечает ботам 403, поэтому не подключён. Условия использования данных каждого сайта стоит уточнить до публичного запуска.

Свой сайт добавляется без кода, файлом `data/sources.json` (формат и параметры `follow`/`tz_mode` описаны в `app/sources/sites.py`).

## Подробнее про culture.ru

Федеральная афиша [culture.ru](https://www.culture.ru/afisha/respublika-bashkortostan)
по Башкортостану (события публикуют сами учреждения культуры):

```powershell
.\.venv\Scripts\python.exe -m app.sync culture-ru --dry-run             # посмотреть, что загрузится
.\.venv\Scripts\python.exe -m app.sync culture-ru --pages 10            # ~200 ближайших событий (20 на страницу)
.\.venv\Scripts\python.exe -m app.sync culture-ru --pages 10 --drop-demo  # то же, но без выдуманных демо-событий
```

Повторный запуск безопасен: события обновляются по ссылке, а не дублируются. Для регулярного обновления поставьте команду в
планировщик задач, например раз в несколько часов.

Как устроен обход (`app/sources/culture_ru.py`): данные берутся из JSON, встроенного в страницу афиши (`__NEXT_DATA__`),
без обхода закрытых разделов. Перед запуском читается `robots.txt` (если запрещено или не прочитался, обход не начинается),
между страницами пауза 1,5 с, запросы идут с User-Agent `bashafisha-hackathon`. Время событий приходит в UTC и переводится в Уфу.

Что важно знать об источнике:
* в карточке только **ближайший сеанс**, а не всё расписание;
* **статусов** (отмена, перенос) и **описаний** в списке нет, поэтому поля пустые: ничего не выдумываем;
* у постоянных выставок есть только дата окончания, началом считаем день синхронизации;
* у некоторых событий в качестве города указан район («Гафурийский район»);
* адаптер ходит **напрямую, в обход системного прокси** (российский сайт через зарубежный прокси недоступен);
  чтобы использовать прокси из окружения, задайте `AFISHA_USE_PROXY=1`;
* формат страницы может измениться: тогда синхронизация остановится с понятной ошибкой, а не загрузит мусор.
  Условия использования данных culture.ru стоит уточнить до публичного запуска.

## Загрузка из файлов

```powershell
.\.venv\Scripts\python.exe -m app.ingest events.json    # или events.csv
```

Формат записи: `title`, `start_at`, `source` (обязательны), далее `description`, `category`, `city`, `venue`, `address`,
`end_at`, `price_min`, `price_max` (0 = бесплатно, пусто = неизвестно), `age_limit` (`12` или `"12+"`), `kids_friendly`,
`url`, `image_url`, `status`. Любой новый источник (сайт театра, музея) пишется как адаптер, который собирает записи в этом формате
(образец: `app/sources/culture_ru.py`), остальное (нормализация, дедупликация, статусы) уже сделано.

## Тестовые данные

Сервис не показывает выдуманных событий: первый запуск использует `data/sample_events.json` (реальные афиши, источник записан у
каждой записи; пересоздать выгрузку из своей базы: `python scripts/export_sample.py`).

Выдуманные события нужны только автотестам и лежат в `tests/demo_data.py`, в образ они не попадают. Если такие события всё же
попали в локальную базу (`python -m tests.demo_data`), интерфейс, бот и виджет помечают их значком «демо», а
`python -m app.maintenance demo-reset --apply` удаляет только их, реальные не трогает.

## Что не сделано

* Данные дают три источника (culture.ru, Яндекс Афиша, Kassir.ru), адаптер KudaGo проверен только тестами. Сайты театров, музеев и
  министерства подключаются тем же способом, но не написаны.
  Расписание сбора есть (`python -m app.scheduler`), но работает только пока запущен процесс, а с российского сервера открываются не все источники. Пометка пропавших событий включена у Kassir.ru и срабатывает после первого прохода.
* **Метрики агента на модели измерены один раз** (`gemini-3.5-flash-lite`, см. «Выбранный уровень решения»): 2 порога не
  выполнены, исправления после прогона ещё не перемерены; 10 внешних запросов и стоимость в рублях не посчитаны. Более ранняя попытка прогнать набор
  (13.11.2026) остановилась на квоте: ключ на бесплатном тарифе даёт 5 запросов в минуту и 20 в сутки, модель успела ответить
  на 8 из 60 запросов (задержка 2,5–23,8 с, медиана около 13 с, 3 000–15 400 токенов на ответ), остальные ответили правила. Эти
  цифры не метрики модели, отчёт сохранён как недействительный (`eval/reports/2026-11-13-llm-quota-incomplete.md`). Для полного
  прогона нужен ключ с платным тарифом или лёгкая модель с большей суточной квотой (набор из 60 запросов это около 80 вызовов
  модели и более). Бот проверен тестами и запущен в Telegram.
* PostgreSQL не проверялся (код написан на SQLAlchemy, поиск по тексту использует только `LIKE`).
* Состояние бота (выбранный город, история диалога) и лимитер запросов живут в памяти процесса.
* Админ-методы защищены общим или личными ключами из `.env` (добавить администратора можно только правкой файла и пересозданием контейнера); модератор может войти и аккаунтом с ролью (без ключа), роли и ключи Министерства выдаёт только владелец ключа ([docs/08](docs/08-аккаунты-и-роли.md)).
* Цепочка моделей: основная Gemini, её запасные модели, затем Groq (бесплатный тариф ограничен 8000 токенов в минуту), затем режим правил: при блокировке запроса, лимитах или недоступности всех провайдеров агент отвечает по правилам. Основная модель с 13.11.2026 `gemini-3.5-flash-lite` (один пробный запрос 0,9 с, на `gemini-2.5-flash-lite` ключ получает 404; полного замера задержки и дневного лимита нет); `gemini-4-hydrogen` (28–31 с на ответ, 20 запросов в сутки на бесплатном ключе) стоит последней в запасных.
