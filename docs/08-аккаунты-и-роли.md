# 08. Аккаунты и роли (план, не реализовано)

Записано 13.11.2026 по просьбе владельца проекта. Это требование и предложение по устройству, кода пока нет.

## Требование

1. **Сайт работает без аккаунта**, как сейчас: поиск, карточки, чат, планировщик, виджет, API. Ничего из этого не закрывается за входом.
2. **Аккаунт нужен тем, кому он что-то даёт:** в аккаунте **история посещений**, подписки и сохранённые условия поиска доступны с любого устройства.
3. **Роли из ТЗ (§3):** Житель, Гость республики, Организатор, Модератор, Министерство. У каждой свои возможности (таблица ниже).
4. Персональные данные минимальны (ТЗ §10, красная линия §13: «сбор персональных данных без необходимости»). История посещений это персональные данные: она включается только по согласию, хранится ограниченный срок, удаляется кнопкой.

## Роли и что они получают

| Роль (ТЗ §3) | Аккаунт | Что даёт |
|---|---|---|
| Гость сайта | не нужен | всё публичное, как сейчас |
| Житель, Гость республики | по желанию | история посещений, подписки на любом устройстве, сохранённые поиски, «избранное» |
| Организатор | да | отправка заявки или уточнения (`save_feedback`), список своих обращений и их статус «принято / в работе / ответ», подтверждение ответственным |
| Модератор | да | то, что сейчас делает админка: очередь, правка, импорт, журнал, сбор. Журнал пишет аккаунт, а не имя из `ADMIN_USERS` |
| Министерство | да (служебный) | чтение данных и API-ключи для встраивания: личный ключ с лимитом, статистика обращений, доступ к документации виджета. Без прав записи |

Различие «Житель» и «Гость республики» только в сценарии (по ТЗ они ищут по-разному), права одинаковые: это один тип аккаунта `user`, различия в подсказках интерфейса.

## Как входить

Рекомендация: **Telegram как основной вход**, потому что бот и мини-приложение уже есть, а подпись `initData` у нас проверяется (`app/telegram_auth.py`).

* Житель, гость, организатор: вход через Telegram (кнопка Telegram Login на сайте, автоматически внутри мини-приложения). Паролей нет, хранить нечего. Номер телефона и почту не просим.
* Модератор, Министерство: тот же вход через Telegram плюс список разрешённых номеров Telegram, которых администратор назначает на роль. Запасной вход: личный ключ (как сегодня), хранится хешем, а не открытым текстом.
* Позже, если понадобится: вход по ссылке на почту (нужна отправка писем).

Вопрос к владельцу: нужен ли вход без Telegram (почта) на первом этапе. Он сильно увеличивает объём (письма, защита от подбора, восстановление).

## Данные

| Таблица | Поля | Заметки |
|---|---|---|
| `users` | id, telegram_id, display_name, role (`user`, `organizer`, `moderator`, `ministry`), created_at, last_seen_at, history_enabled, deleted_at | имя из Telegram, без телефона и почты |
| `sessions` | token_hash, user_id, expires_at | кука `HttpOnly`, `SameSite=Lax`; в базе только хеш |
| `visit_history` | user_id, event_id, viewed_at | пишется только при `history_enabled`; без дублей за сутки; хранится 90 дней |
| `saved_searches` | user_id, filters (JSON), name | то же, что фильтры подписок |
| `api_keys` | key_hash, owner_user_id, scopes, rate_limit, revoked_at | для роли «Министерство» и модераторов, показывается один раз при создании |
| `feedback.user_id` | ссылка на автора обращения | у организатора есть список и статусы |

Подписки (`subscriptions`) привязываются к `user_id`, а не только к номеру чата Telegram. Подписка из бота и с сайта становится одной записью.

## Что меняется в приложении

* **Права.** Вместо одной проверки `require_admin` появляется проверка роли: `require_role("moderator")`. `ADMIN_API_KEY` и `ADMIN_USERS` остаются как аварийный вход до переноса модераторов в аккаунты.
* **Журнал** (`audit_log`): актор записывается как `user:<id>`, имя берётся из аккаунта.
* **История посещений:** запись при открытии `/event/{id}` и карточки в мини-приложении, если пользователь вошёл и включил историю. Страница «Мои посещения» с кнопками «Очистить» и «Скачать (JSON)».
* **Приватность:** кнопка «Удалить аккаунт» стирает пользователя, историю, сохранённые поиски и подписки; срок хранения (90 дней для истории) указан в README.
* **Админка:** вкладка «Пользователи» для администратора: назначить роль, отозвать доступ, выдать или отозвать API-ключ.
* **Бот:** уже знает `chat_id`, связывается с аккаунтом при первом входе через Telegram.

## Порядок работ (оценка)

1. Таблицы, миграция 0005, вход через Telegram, сессии, `GET /api/v1/me`, выход. Сайт работает как раньше. (~½ дня)
2. История посещений и «Мои посещения», согласие, очистка, экспорт, удаление аккаунта; подписки привязаны к `user_id`. (~½ дня)
3. Роли: `require_role`, перенос модераторов на аккаунты, вкладка «Пользователи», выдача API-ключей Министерству. (~½–1 день)
4. Организатор: личный список обращений и статусы, уведомление о ответе в бот. (~½ дня)
5. Тесты, документация, обновление README (срок хранения, перечень ПД), выкладка. (~½ дня)

## Риски и вопросы

* Вход через Telegram на сайте требует домен, привязанный к боту (`/setdomain` у BotFather); `sslip.io` для этого годится, но для постоянной работы нужен свой домен.
* Мини-приложение уже даёт вход «бесплатно»: в нём аккаунт создаётся при первом открытии. Нужно решить, делать ли это молча или с вопросом о согласии на историю (рекомендуется вопрос).
* Что считать «посещением»: открытие карточки, переход по ссылке на билеты или оба. Рекомендация: открытие карточки и переход по ссылке источника, оба с отметкой типа.
* Рассылка (ТЗ §14: уведомления об отменах) естественно ложится на аккаунты и сохранённые подписки.
* Юридически: нужны согласие и политика обработки данных; формулировку согласовать с заказчиком (Приложение В ТЗ).
