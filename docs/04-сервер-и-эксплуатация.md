## Главная особенность: сервер в России

### Обратный SSH-туннель (самое хрупкое место)

Прокси живёт на домашнем компьютере (`127.0.0.1:10809`). Туннель пробрасывает его на сервер. Готовый скрипт: `powershell -ExecutionPolicy Bypass -File deploy	unnel.ps1 -Key "<путь к .pem>"` (то же, что цикл ниже):

```powershell
$key = "<путь к .pem>"
while ($true) {
  ssh -i $key -N -R 127.0.0.1:10809:127.0.0.1:10809 `
      -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=4 -o ConnectTimeout=20 `
      ubuntu@195.209.220.227
  Write-Output "$(Get-Date -Format s) tunnel dropped (exit $LASTEXITCODE), reconnecting in 5s"
  Start-Sleep -Seconds 5
}
```

* Работает **только пока включён компьютер и идёт этот цикл**. Выключили компьютер, закрыли окно: туннеля нет.
* **Нет туннеля**: бот молчит (контейнер `afisha-bot` перезапускается по кругу: при старте он обращается к Telegram), чат на сайте отвечает «в режиме без ИИ» (по правилам), всё остальное работает.
* Проверка на сервере: `ss -tln | grep 10809` (должна быть строка LISTEN) и `curl -s -o /dev/null -w "%{http_code}" -x http://127.0.0.1:10809 https://api.telegram.org` (ответ 302 = прокси жив).
* Побочный эффект: порт 10809 на сервере открыт для всех процессов сервера, включая чужой проект. Это свойство схемы.
* **Постоянное решение**: зарубежный VPS (Нидерланды, Польша, Франция и т. п.; хватит 1 vCPU / 1 ГБ, около 343 ₽/мес за год). Там Telegram и Gemini доступны напрямую, туннель и прокси не нужны, всё приложение переезжает целиком (`deploy/run.sh` без `HTTPS_PROXY`/`TELEGRAM_PROXY`).

## Выкладка новой версии

С домашнего компьютера (Git Bash). Тесты сначала: `python -m pytest`.

```bash
cd afisha
KEY="<путь к .pem>"
tar czf release.tgz --exclude='__pycache__' app data/venues.json requirements.txt Dockerfile deploy README.md .env.example
scp -i "$KEY" release.tgz ubuntu@195.209.220.227:/tmp/release.tgz && rm release.tgz
ssh -i "$KEY" ubuntu@195.209.220.227 'bash -s' <<'EOF'
set -e
STAMP=$(date +%Y%m%d-%H%M%S); BK=~/afisha-backup-$STAMP; mkdir -p $BK
cp -a ~/afisha/app ~/afisha/Dockerfile ~/afisha/requirements.txt ~/afisha/.env ~/afisha/.env.bot ~/afisha/data/afisha.db $BK/
sudo docker tag afisha:latest afisha:prev
cd ~/afisha && rm -rf app.new && mkdir app.new && tar xzf /tmp/release.tgz -C app.new && rm /tmp/release.tgz
rm -rf app deploy && mv app.new/app app.new/deploy . && mkdir -p data && mv app.new/data/venues.json data/ && mv app.new/requirements.txt app.new/Dockerfile app.new/README.md app.new/.env.example . && rm -rf app.new
bash deploy/run.sh
EOF
```

`deploy/run.sh` собирает образ, пересоздаёт оба контейнера с урезанными правами и проверяет `/api/health`.

Заметки по заливке с Windows:
* Git Bash `tar czf C:/путь/…` воспринимает `C:` как имя удалённого хоста: создавайте архив в текущем каталоге с относительным именем.
* Скрипт, переданный из PowerShell в `ssh … "bash -s"`, получает BOM в начале и `\r` в конце: начинайте скрипт с безобидной строки `true`, а из Git Bash используйте heredoc, как выше.
* Если менялся nginx: скопировать `deploy/nginx-afisha.conf` в `/etc/nginx/conf.d/afisha.conf`, обязательно `sudo nginx -t`, и только потом `sudo systemctl reload nginx`; при ошибке вернуть копию из резервной папки.

Если только статика (`app/static`): достаточно пересобрать образ и пересоздать `afisha-web` (бот статику не использует).

**Первая выкладка версии с сериями показов и подписками.** Новый столбец `events.series_until` и таблица `subscriptions` создаются сами при старте (`init_db`). Серии, уже лежащие в базе как длинный период, исправляются один раз (резервная копия базы делается скриптом выше):

```bash
sudo docker exec afisha-web python -m app.maintenance series            # посмотреть
sudo docker exec afisha-web python -m app.maintenance series --apply    # исправить
```

Рассылку подписчикам запускает сам бот, отдельных заданий не нужно.

**Выкладка версии с API v1, админкой, журналом и формой обратной связи.** Новые таблицы (`raw_records`, `audit_log`, `feedback`) и столбцы (`events.publication`, `events.venue_key`) создаются и заполняются при старте. Дополнительно:

1. В `.env` задайте личные ключи модераторов `ADMIN_USERS=имя:ключ,…` (или `ADMIN_API_KEY`), пересоздайте контейнеры (`bash deploy/run.sh`).
2. Обновите конфиг nginx: `cp deploy/nginx-afisha.conf /etc/nginx/conf.d/afisha.conf`, подставьте домен и пути сертификата, `sudo nginx -t`, затем `sudo systemctl reload nginx`. Новое в конфиге: журнал доступа без адресов посетителей (`/var/log/nginx/afisha.access.log`, формат `afisha_noip`), сквозной `X-Request-ID`, закрытый снаружи `/metrics`, увеличенный размер тела для `/api/v1/admin/import`.
3. Проверка: `curl -s http://127.0.0.1:8001/api/v1/health`, `curl -s http://127.0.0.1:8001/metrics | head`, `https://<домен>/admin` (ключ в поле входа), `https://<домен>/event/1`.
4. Логи приложения: `sudo docker logs --tail 20 afisha-web` (одна JSON-строка на запрос, без адресов и текстов запросов). По жалобе пользователя ищите его `X-Request-ID` в логах и в `/admin` → «Журнал изменений».

## Обновление данных (culture.ru)

С сервера нельзя (см. выше), поэтому:

1. На домашнем компьютере: `python -m app.sync culture-ru --pages 10`. Если не стартует (таймаут рукопожатия, 503 на `robots.txt`), **сайт-источник временно недоступен: подождать и повторить, обход правил не делать**.
2. Свежую локальную `afisha.db` загрузить на сервер: сначала резервная копия серверной (`cp data/afisha.db …`), затем остановить `afisha-web` и `afisha-bot`, заменить файл (владелец `ubuntu`, права 600), запустить `bash deploy/run.sh`.
3. Проверить `/api/meta` (число событий) и сайт.

Автоматического расписания нет (планировщик задач на сервере не заводился), события, пропавшие из источника, сами не удаляются.

**Проверка 13 ноября:** с сервера открываются Яндекс Афиша и Kassir.ru (robots.txt отвечает 200), culture.ru тоже отвечал; KudaGo отвечает 403 (из России закрыт, не обходим). Значит, `python -m app.sync all` можно запускать и на сервере, внутри контейнера `afisha-web`, без домашнего компьютера (загрузчик ходит напрямую, прокси не нужен); расписание (cron) заводится только с вашего согласия.

## Резервные копии и откат

* Перед каждой выкладкой: `~/afisha-backup-<дата-время>/` (код, оба `.env`, база, старый конфиг nginx) и образ `afisha:prev`. Сейчас есть копия `afisha-backup-20261111-222939` (состояние до включения защиты).
* **Откат кода**: вернуть `app`, `Dockerfile`, `requirements.txt` из резервной папки в `~/afisha`, выполнить `bash deploy/run.sh`. Быстрее, если нужен именно прежний образ: `sudo docker tag afisha:prev afisha:latest` и пересоздать контейнеры.
* **Откат базы**: остановить контейнеры, вернуть `afisha.db` из папки, запустить.
* **Откат nginx**: вернуть `nginx-afisha.conf.bak`, `nginx -t`, `reload`.
* Старые резервные папки накапливаются: удалять руками, когда новая версия проверена.

## Если что-то сломалось

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Бот не отвечает, контейнер `Restarting` | нет туннеля | поднять туннель; бот оживёт сам |
| В логе бота «ПОДПИСКА НЕ ПРОВЕРИТЬ» | бот не администратор канала | назначить бота администратором `@sz_orenteam` |
| В чате «Режим без ИИ» | нет туннеля, ключ Gemini невалиден, суточный бюджет ИИ исчерпан, или Gemini перегружен (503 UNAVAILABLE) | смотреть `docker logs afisha-web` (строка «Gemini не сработал»); перегрузка Gemini временная |
| «слишком много шагов инструментов» в логе | модель зациклилась на поиске, ответ ушёл по правилам, ~1 минута задержки | ограничено временем и шагами; при частых случаях сузить промпт/инструменты |
| 429 на сайте | сработал лимит запросов | подождать минуту |
| Сайт отвечает 400 на запросы | `ALLOWED_HOSTS` не содержит имени, по которому зашли | добавить имя в `.env`, пересоздать `afisha-web` |
| Приём данных отвечает 503 | `ADMIN_API_KEY` пуст или короче 24 символов | задать длинный ключ в `.env`, пересоздать контейнер |
| Данные устарели | автообновления нет | см. «Обновление данных» |
| Сертификат истекает | certbot не продлил | `sudo certbot renew --dry-run`, смотреть таймер certbot |
| Gemini отвечает 403 `API_KEY_SERVICE_BLOCKED` | ключ ограничен/заблокирован | создать новый ключ в AI Studio, обновить `.env` и `.env.bot` на сервере и локально |

Изменение `.env` на сервере подхватывается только после пересоздания контейнера (`bash deploy/run.sh`).
